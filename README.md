# Huzige Daily Newslet

《胡子哥财经晨报》生产流水线 —— 每天 4 张竖版卡片，**数据 → HTML → PNG → 版面体检**一条龙。

面向香港保险潜在客户的跨境财富简报。读者在手机上看，不在电脑上看 —— 所以所有字号、栅格、
配色都按**整幅长图在手机上读得清**校准过，不假设任何二次裁切。

```
┌─────────────────────────────┐
│ banner  118px  #800000      │  ← 品牌名（中/英同宽）+ 期号 + 日期
├─────────────────────────────┤
│   正文页 1080 × 1440（3:4）  │  ← 主标题 / 条目区 / 结论条 / 口径注 / 角标
├─────────────────────────────┤
│ footer  ~150px  #F1EDE2     │  ← 本页数据来源 + 风险声明 + 微信二维码
└─────────────────────────────┘
```

合计 1080 × 1735（CSS），2× 导出为 2160 × 3470 PNG。

## 跑之前先自查同步

```bash
bash scripts/sync_check.sh
```

逐文件比对本地与 GitHub 最新 Release 的 blob sha（不只是看版本号），
告诉你**哪里不一致**：

```
 ✅ 已同步 —— 本地与 GitHub 最新 Release 完全一致
 ⚠️  内容不同（2）：~ SKILL.md  ~ references/checklist.md
 ⚠️  仅本地有（1）：+ scripts/publish.sh
```

退出码 `0` 已同步 / `1` 有差异 / `2` 查不到远端。

**这是「用哪版代码产出」的守门闸** —— 不一致就说明你跑的是旧逻辑，
出的图和文档对不上。差异的处理见下面「版本发布规则」。

## 版本发布规则

**三条铁律**

1. **改只在本地做** —— 改本机 skill 目录，不直接改 git 仓库、不在 GitHub 上编辑
2. **确认后才上传** —— 改完先确认，等明确指令再发布。改 ≠ 发布
3. **每次上传必须更新 Release 版本** —— 只推 tag 不建 Release 视为没发完

**发布**

```bash
# 1. 改本机目录
# 2. 演一遍
bash scripts/publish.sh --dry-run

# 3. 正式发（会问版本号、要求确认）
bash scripts/publish.sh

# 4. 核验
bash scripts/sync_check.sh
```

`publish.sh` 把本地目录同步进工作副本 → 列出改动 → bump `VERSION` → 提交 → 打 tag →
推送 → 建 Release → **核验三项**（推送成功 / tag 在远端 / Release 存在，缺一即未完成）。

**版本号**：semver，写在 `VERSION` 文件。修 bug → patch（1.0.0→1.0.1）；
加功能 → minor；改结构 → major。**改了内容就必须 bump** —— 否则别人拉到的包
「内容变了但版本号没变」，没法判断新旧。

**改规则的连带同步（最容易漏）**：改一条规则要 grep 全库确认无残留，
共 5 处：`SKILL.md` / 三份 `references/*.md` / **`templates/data.template.json`** /
代码与注释 / `README.md`。模板不是文档的附属品，是生产入口。

## 快速开始

```bash
# 1. 装依赖
cd ~ && npm i playwright && npx playwright install chromium

# 2. 复制模板，填这一期的数据
cp templates/data.template.json <你的工作目录>/data.json

# 3. 一条命令跑完：算账 → 重建 → 渲染 → 体检 → 估算对照
./scripts/make.sh
```

跑完 `cards/` 里会有 4 个 HTML + 4 个 PNG（`card-01.png` ~ `card-04.png`）——**这就是全部交付物**。

`make.sh` 会自动探测 node / python 路径，失败即停，只给摘要。四种用法：

| 命令 | 作用 |
|---|---|
| `./scripts/make.sh` | 全流程 |
| `./scripts/make.sh plan` | 只看竖向预算账，不动文件 |
| `./scripts/make.sh dry` | 只跑文案预检，不写 HTML |
| `./scripts/make.sh 4` | 只处理第 4 张 |

想分步跑（或改脚本本身时）：

```bash
python3 scripts/build_cards.py data.json -o cards/   # 数据 → HTML（含预检 + 预算分配）
node scripts/render.cjs cards/                       # HTML → PNG
node scripts/audit_layout.cjs cards/                 # 版面体检（九项）
node scripts/doctor.cjs cards/ --verbose             # 真实行数 / 留白 / 标签配色
python3 scripts/doctor.py data.json cards/           # 预算账 vs 实测，逐项对照
```

**排查问题时先跑现成工具，不要临时写量测脚本** —— `make.sh` / `doctor.*` 覆盖了九成排查动作。

## 四张卡片结构

| # | 段落 | 条目数 | 内容 |
|---|---|---|---|
| 01 | 今日三条 | 3 | 汇率 / 利率 / 油价 |
| 02 | 隔夜市场温度 | 2 | 宽件（十项指标网格）+ 窄件（换汇窗口大数字） |
| 03 | 今日三件事 | 3 | 原油 / 美债 / 美股 |
| 04 | 保险与税务观察 | 3 | 家办生态 / 融资放大保单的传导链 / 税后 ≠ 到手 |

02 号只放两条是刻意的：十项指标网格本身要 767px，再加一条就会把格子压到叠字。
**条目数不是越多越好，是「密度装得下」才多。**

## 核心设计原则

### 1. 占屏比例由内容密度决定，不可手填权重

早期用 `w: 1.75` 这样的手填权重，把版面决策交给数据作者 —— 内容改了权重没跟着改，
十项网格被压到叠字而下面那条空掉半张。

现在高度由 `visual_natural_h()` 按视觉件类型与内容量算出自然高度，
再由 `allocate_heights()` 分给各条。**密度大的自然占大面积。**

### 2. 左右两栏取大值，不是相加

左右两栏是**并排**的，所以一条的需求是 `max(左栏文字, 右栏视觉件)`。
漏掉左栏的后果很具体：加了要点层之后左栏比容器高，第三条要点直接被裁掉。

### 3. 三层文字结构，各司其职

| 层 | 字段 | 字号 | 写什么 | 不写什么 |
|---|---|---|---|---|
| 结论层 | `title` | 36px 粗 | 是什么 | 不写细节数据 |
| 钩子层 | `desc` | 28px | 一句钩子（≤18 字，单行） | 不重复 title，不堆数据 |
| 要点层 | `points[]` | 24px 灰 | 具体数据、对比、判断 | 不重复 title / desc |

`desc` 压到单行是硬要求 —— 它占 2 行就是 84px，是左栏最大的单项开销；
压到 1 行后省下的 42px 正好够再放两条要点。**信息量不减反增**，数据全部下沉到要点层。

要点装不下时**自动降档**（少渲染一条），**绝不裁字** —— 裁字比少一条难看得多。

### 4. 视觉件内部按可用高度降档，不写死字号

环形百分比字号由 Python 按**内径**算好后内联，CSS 里写死 `font-size:46px` 会盖掉内联，
数字直接压在环上。字号下限跟内径联动。

### 5. 文字宽度按浏览器实测系数算

`em_width()` 的系数是实测的（PingFang SC 24px）：
**汉字 1.0 / 数字 0.575 / 拉丁字母 0.544 / 斜杠句点 0.52 / 空格 0.333**。

之前一律按 0.56 算，数字被低估 —— 46 字的口径注实际 2 行却估成 1 行，
note 少算 38px，最后一条讯息被下面的角标压掉一截。
`est_lines()` 另留 3% 安全余量：宁可估多一行（版面略松），不能估少（内容被裁）。

## 三条硬约束

1. **不荐股荐基** —— 不点名评级、不给目标价、不说「建议买入」
2. **不推销保险** —— 不出现具体产品名与收益演示；比较只比结构不比公司
3. **不搬运** —— 每条都带一句自己的判断，哪怕判断是「这条对你的换汇节奏没影响」

内容只负责让人相信「你懂海外金融」。卖货动作放在一对一私聊里。

## 微信二维码

`assets/wechat-qr.png` 是本仓库作者的微信二维码，脚本会自动内联成 base64。

## 已知踩坑（改代码前先看这条）

- **CSS 里不能直接写 `%`**：样式表用 `%` 做字符串插值，所有百分号必须写成 `%%`（含注释里的）。
- **`.item` 必须 `flex:0 0 auto` + inline 高度**：写成 `flex:1` 会把 Python 算好的分配全部作废。
- **SVG 的 viewBox 跟 flex 容器对不上就会被压扁**：折线件因此改用百分比坐标 + HTML 绝对定位。
- **SVG 里的文字会随 viewBox 一起缩小**：环形件「76.1%」改用 HTML 绝对定位叠在圈心。
- **纵向 flex 里 `flex-basis:100%` 指的是高度不是宽度**：要占满整行请写 `width:100%`。
- **大数字必须做宽度兜底**：「109.16 美元」用 104px 会横向溢出 24px。
- **按比例分配必须逐条封顶**：`give = min(head[i], ...)`，否则一条会抢走全部富余。
- **小字是四图的头号隐形杀手**：19–21px 在 1080 画布上看着还行，手机上只有 6.8–7.6pt。
- **`find` 排除目录要写 `-not -path '*/__pycache__/*'`**：`./__pycache__/*` 只挡根目录，
  实际 pycache 在 `scripts/` 下会漏掉；`-not -name '__pycache__'` 也不行（只匹配文件自身，
  不匹配目录内容）。`sync_check.sh` 踩过这个坑。
- **冒烟测试脚本要跟随模板形态**：模板从 desc 模式改成 prose 模式后，
  「给所有条目补 desc」的旧脚本会触发 prose+desc 冲突告警。补之前先判 `if not prose and not desc`。

## 整幅阅读，不假设二次裁切

每一张图都是一张**独立可读的长图**。图可能被放在任何位置、被任何客户端以任何方式缩放，
所以版面不依赖「用户点开就能看到全部」这个假设。

由此定下三条：

- **主标题是每张图的第一眼** —— 在正文页顶部，单行，字号 34–52px 自适应
- **核心数字必须在视觉件里** —— 不靠「反正底部会被裁」来安排位置
- **banner 与 footer 都是内容** —— 不是装饰，也不是留白

早期整套版面是按「朋友圈 2×2 缩略图只显示中心 1:1」校准的，于是推出过两条错误结论：
「主标题会被切掉」和「核心数字必须落在 206–1286」。这个渠道假设已经不成立，
那两条结论连同大片预留死区一起作废。

> 将来要发到某个会二次裁切的渠道，**不要改回旧逻辑**——另出一版适配那个渠道的图，
> 而不是让主图迁就某一个渠道的裁切规则。
