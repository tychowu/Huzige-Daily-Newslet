## 2. 三段落栅格

一张图 = 三段，总高 **1735**（CSS 像素）：

| 段 | 高度 | 位置 |
|---|---|---|
| banner | 118 | 页面范围外，顶部 |
| 正文页 | **1440（严格 3:4）** | 主体 |
| footer | ≈ 177 | 页面范围外，底部 |

- 画布宽 **1080**，2× 导出 **2160×3470**
- 正文页左右安全边距 **68px**
- 条目卡片：内边距 18px 上下 / 22px 左右，条目之间 gap 12px
- 条目左栏（文字）可用宽 **900**；右侧视觉件列固定 **356px**，内边距 14px，实际可用 **328px**
- 标题用衬线（Songti SC），正文与数字用无衬线（PingFang SC）

正文页内部只有五层，自上而下：**主标题 → 条目区（2–3 条）→ 结论条 → 口径注 → 右下角段落名角标**。
段落名**不再单独起一行**（早期 `.p-head` 已删），改成正文页右下角的角标胶囊。

## 3. 竖向预算：谁分到多少高度

正文页 1440px 是有限的，条目区的高度在 Python 端**先算死**再画：

```
stack_h = 1440 − PAD_T(44) − PAD_B(34) − 主标题高 − 结论条高 − tailrow高 − 条目间距
```

`tailrow` 是**口径注 + 右下角角标并排的那一行**（`.tailrow`，`space-between`），
高度取两者较大值 + 10px margin。原来两者各占一行，白白吃掉 50px。

剩下的 `stack_h` 由 `allocate_heights()` 按**内容密度**分给各条，不手填权重。

**这条规则是「不许留白」的技术保证**：视觉件不需要自己猜高度，它拿到的就是最终高度。

| 高度常量 | 值 | 说明 |
|---|---|---|
| `PAGE_H` | 1440 | 正文页严格高度 |
| `PAD_T` / `PAD_B` | 44 / 34 | 正文页上下内边距 |
| `HEAD_GAP` | 14 | 主标题与条目区间距 |
| `ITEM_GAP` | 12 | 条目之间间距 |
| `ITEM_PAD_V` / `ITEM_PAD_H` | 18 / 22 | 条目卡片内边距 |
| `IT_R_W` / `IT_R_PAD` | 356 / 14 | 视觉件列宽与内边距 |
| `ITEM_CHROME` | 38 | `ITEM_PAD_V×2 + 2`（item 自身 padding + 边框） |
| `VIS_CHROME` | 28 | `IT_R_PAD×2`（视觉件容器 padding） |
| `CHROME` | 66 | `ITEM_CHROME + VIS_CHROME` |

### 左栏与右栏取大值，不是相加

左右两栏是**并排**的，所以一条的需求是 `max(左栏文字, 右栏视觉件)`。

左栏由 `left_natural_h(item, w_left)` 算：

| 左栏成分 | 高度 |
|---|---|
| 眉标行 | 40 |
| 结论句 | `行数 × 47`（36px × 1.3） |
| 解释句 | `行数 × 42`（28px × 1.5） |
| 要点层 | 23（分隔线 + padding）+ `条数 × 35` + `间隔 × 9` |
| 子元素 gap | `(子元素数 − 1) × 7` |

**漏掉左栏的后果**：加了要点层之后左栏比容器高，第三条要点直接被裁掉，
体检报 `溢出 div.it-l 里的 div.pt 顶出 40px`。

### 分配算法

1. `visual_natural_h(item, w)` 算出每条的**自然高度**（左栏与右栏取大者）
2. 每条先拿到自己的需求 `need`
3. 富余在各自**上限** `cap` 内摊开（**逐条封顶**，见下）
4. 摊不掉的富余给**弹性件**（宽表 grid）
5. 高度和**精确对齐**到 `stack_h`，绝不超过

| 视觉件 | 自然高度（净高） | 上限系数 |
|---|---|---|
| `grid` | `行数 × 73 + 文字块 + 14`（**下限**，见下） | 1.42 |
| `steps` | `节点数 × 86 + 12` | 1.22 |
| `bar` | `条数 × 92 + 20` | 1.34 |
| `num` | `96 + 附属数 × 76 + 25` | **1.15**（最紧） |
| `line` | `92 + 128 + 42` | 1.34 |
| `ring` | `max(环直径, 侧栏行数 × 62)` | 1.20 |

### 宽表件（grid）是弹性件

`grid-auto-rows:1fr` 会把网格**拉伸填满**容器。所以：
- 73px/行只是**下限**（格子不被压扁的底线），不是等高
- 宽表件负责**吸收剩余高度**（代码里的 `elastic` 列表）
- 窄件先各拿够自己的需求，剩下的才给宽表件

宽表件的高度公式：`文字块 + 间距14 + 网格下限 + ITEM_CHROME + VIS_CHROME`。
少减一项，网格就超出 item，底下的条目被压掉一截（实测溢出 37px）。

### 三个必须遵守的实现约束

**1. `.item` 用 `flex:0 0 auto`，高度写进 inline style。**

```css
/* 对 */  .item{ ... flex:0 0 auto; }
/* 错 */  .item{ ... flex:1 1 0; }   /* 浏览器把分配结果全作废 */
```

**2. `item_h`（item 总高）与 `vis_h`（视觉件净高）分开传。**

`render_item(item, w, item_h, base_dir, idx, vis_h=None)`。
混用会让 item 实际高度比预算少一截——`.items` 是 `flex:1`，子项总高不够时
空白全部落在条目区底部，形成一条 200px 高的空带。

**3. 迭代必须有上限。**
`allocate_heights()` 里按比例分配用整数除法，每次截断零点几像素，
`rest` 可能一直 > 1 收不住——`while` 会变成活锁，脚本被 SIGTERM。
一律写 `for _ in range(8)` 并检查收敛。

**4. 按比例分配必须逐条封顶。**

```python
# 错：heights[i] += int(surplus * head[i] / head_sum)
# 对：give = min(head[i], int(surplus * head[i] / head_sum))
```

只有一条 fixed 时 `head_sum == head[i]`，错误写法让这一条拿走全部富余，
直接突破自己的 cap（窄件 339 拿到 643，超上限 389 一大截，页面多出空白）。

### 文字宽度要按实测系数算

`em_width()` 的系数是浏览器实测的（PingFang SC 24px）：

| 字符 | 系数 |
|---|---|
| 汉字 | 1.0 |
| 数字 | 0.575 |
| 拉丁字母 | 0.544 |
| 斜杠／句点等 | 0.52 |
| 空格 | 0.333 |

之前一律按 0.56 算，数字被低估——46 字的口径注实际 2 行却估成 1 行，
note 少算 38px，最后一条讯息被下面的角标压掉一截。

`est_lines()` 另留 **3% 安全余量**（`(width_px × 0.97) / font_px`）。
宁可估多一行（版面略松），不能估少（内容被裁）。

### 竖向零空隙的自检法

```bash
# 条目底边应紧贴 note 顶边，差 100px 以上就是分配没生效
node -e "..."   # 量 .item 与 .note 的 getBoundingClientRect()
```

`audit_layout.cjs` 不查这一项（它查的是元素级溢出），必须目视或单独量。

## 4. 字号（手机阅读下限，不得调小）

| 元素 | 字号 | 行高 |
|---|---|---|
| 视觉件大数字 | **104 起，自动降档到 40** | 1.02 |
| 主标题 | **52 起，单行自适应降至 34 为底线** | 1.28 |
| 条目标题（结论句） | **36** | 1.3 |
| **正文段落（`prose` 连续文字）** | **24** | **1.55** |
| 条目解释（`desc`，旧形态） | **28** | 1.5 |
| 要点（`points`，旧形态） | 24 | 1.62 |
| 眉标 | 26（700） | — |
| 视觉件主数值（`mx-v`/`rs-v`） | 31–32 | 1.1–1.2 |
| 视觉件标注／时间轴 | 22–24 | 1.25–1.45 |
| 网格数值 | 40 | 1.15 |
| 网格指标名 | 25 | 1.25 |
| 网格涨跌／状态标签 | 22–24 | — |

**正文段落层（`.it-prose`）** 是 2026-10-22 起的主形态：24px / line-height 1.55 / `text-align:justify`。
行距比要点层松（1.55 vs 1.62 的视觉差来自段落的块级结构）——中文段落行距挤在一起读起来是「墙」，读者会跳读。
左缩进 `PROSE_PAD=30px`，首行**不缩进**（手机上缩进两格反而挤），整段左对齐。
单条上限 260 字；窄件每条约容 5–6 行（≈100–145 字），宽件通栏 900px 每行约 36 字。
`prose` 与 `desc`+`points` **二选一**，前者优先——同时写会触发预检报警（desc 会被忽略，钩子就丢了）。

banner 区（页面范围外，独立体系）：中文 46 / 英文 21（600 字重，flex 分布撑满同宽）／期号 27 / 日期 23。
footer 区（页面范围外）：来源 19 / 免责 19。

换算：1080px 图在手机上按 ~390pt 宽显示，缩放系数 0.36。**28px 条目解释 ≈ 10.1pt**，可接受；再小就是电脑版。

**正文页内没有任何文字低于 22px**（≈7.9pt）。footer 的 19px 是唯一例外——法定声明，压到 22px 会把 footer 撑高一倍。

**主标题单行规则**：`fit_headline()` 用字宽反推字号（中文 1em、ASCII 0.56em、空格 0.30em），
→`size = max(34, min(52, CONTENT_W / em_total))`，配 `white-space:nowrap`。
折行的唯一解法是砍字，不是缩到 34px 以下。

## 5. 语义标签（全期一个组件）

| 标签 | 含义 | 文字色 / 底色 | 色相 | 对底对比度 |
|---|---|---|---|---|
| 窗口 | 对客户当前动作有利的时点 | `#266C4B` / `#E8F3EC` | 152° 墨绿 | 5.55:1 |
| 高位 | 利率、价格处在历史偏高位置 | `#1F497D` / `#E7EDF5` | 213° 海军蓝 | 7.73:1 |
| 风险 | 需要留意的方向（同「承压」） | `#800000` / `#F7E9E9` | 0° 深红 | 9.27:1 |
| 观察 | 方向不明确（含中性／分化／待验证） | `#8B5B10` / `#FCF3E4` | 37° 金棕黄 | 5.30:1 |

**规格唯一**：24px / 600 / `padding:3px 12px` / `r4`。`.tag`、`.tag-inline`、`.gc-tag`
三处共用，渲染后只允许出现 1 种规格组合（体检脚本会量）。

**2026-10-22 定稿：绿 / 蓝 / 红 / 黄。这是唯一有效版本，不要再自行"优化"色相。**

语义分工靠直觉就成立，不依赖读者读字：

- **绿＝可通行**（开闸、窗口期）
- **红＝警报**（要留意、承压）
- **蓝＝位置**（偏高，但不是风险）
- **黄＝待定**（方向未明）

**对比度梯度是刻意保留的**：风险 9.27 > 高位 7.73 > 窗口 5.55 > 观察 5.30。
红最重所以第一眼落在「风险」上，绿/黄偏轻所以退成背景性状态标注 —— 这是层次，
不是权重不齐。**曾经按"对比度必须齐平"压平过一次，结果整体变闷，已被胡子哥否掉。**

**已知取舍**：窗口绿 `#266C4B` 与「跌」绿 `#1E7B4E` 色相只差 0.7°，同框时靠
**浅绿底色 + 胶囊形状**区分，不靠色相。若要拉开只能往青偏（H160°+），属改用户决定，先问。

**涨跌配色遵守中国习惯**：涨＝红 `#B3261E`，跌＝绿 `#1E7B4E`，不得反用。

位置规则：

- **内联在条目标题行首**，作为一枚小胶囊（`.tag.tag-inline`），不另起一行
- 温度计网格的单元格里各带一枚
- 一个条目最多一枚，不要在解释句中间插标签
- 标签与数值之间留 8px 以上，避免视觉粘连

## 6. 七种迷你视觉件

每条讯息配一个视觉件，列宽 356px。件必须**撑满分到的高度**。

### `line` 迷你折线

大数字 + 走势 + 首末时间标签。给「一个数字讲一件事」用（汇率）。

**实现要点：不用 SVG viewBox，用百分比坐标 + HTML 绝对定位。**
容器高度由 flex 分配，Python 端算不准，viewBox 一旦对不上，图形会等比缩到中间一半宽、
旁边的文字掉出容器。改用 `.mn-plot{position:relative}` + `.plot-svg{position:absolute;inset:0}` +
`.mn-dot{left:X%;top:Y%}`，坐标永远跟着容器走，文字也不受缩放影响。

- 圆点留边：x 方向 4%、y 方向 9%，圆点才不会被容器边缘切掉
- 面积填充保留（`opacity 0.09`），但**面积填充算深红预算里的「可留」档**
- 首末时间标签用 HTML 排（`.mn-axis`，左右分列），不用 SVG text

### `num` 大数字

大数字 + 单位 + 一行说明 + 2–3 条附属统计（`extra`）。

**附属统计是必需的**：视觉面板是有底色的方块，只放一个数字的话面板上下全是空的，看着像没做完。
挂两三条真实数据，面板就被填满了。

- 大数字字号由 `fit_number_size(value, unit, w, cap, avail_h)` 按**宽度和高度双约束**算出。
  只看宽度会算出偏大的字号——`line-height:1.02` 让实际占位比字号多 2%，
  再加上附属统计的行高，最后 10px 被裁掉。
- **高度换算**：附属统计每行 76px（32px 数值 + 23px 说明 + 11px 间距），
  `.mx` 自身还有 25px（上边距 13 + 分隔线内边距 12）。
  `avail_h = 视觉件净高 − 附属行数 × 76 − 25 − 22`。
- `mx` 附属统计块用 `flex:1` + `justify-content:space-evenly`，分掉大数字下面的空档

### `bar` 横向条

三种模式，**别用错**：

| mode | 语义 | 画法 |
|---|---|---|
| `center` | 涨跌分化（0 在中轴） | 0 在正中，负值用 `.mb-left{margin-left:auto}` 往左长 |
| `level` | 两个水平值对比（曲线更平） | 从 0 起长，能看出「几乎一样高」 |
| `max` | 占比构成 | 全部按最大值归一 |

**百分比与绝对量不能混在同一根轴上**——混了读者会读错。
`mb-row` 用 `flex:1` 均分整列高度，条本身 22px 高。

### `steps` 因果链

2–4 步，每步 = 编号圆 + 文字。

**节点与连接线平铺成同级兄弟**：节点固定高（`flex:0 0 auto`），连接线 `flex:1` 吸收富余高度，
一根贯通的线把节点串起来，箭头收尾。

早期写法是「节点+连接线」打包成组（`.ms-group`）、组用 `flex:1` 均分整列——**只剩 2 个节点时每组空出一半**，
连接线又固定 14px，整段看起来是「两个孤零零的框 + 什么都没有」。不要用那个写法。

最后一步用红底（`tone:"risk"`）。

### `ring` 环形进度

左环 + 右侧数据列。给概率类用（加息定价 76.1%）。

**圈只画圈，百分比用 HTML 绝对定位叠在圈心**（`.mn-ringmid`）。
SVG viewBox 里的文字会随 viewBox 一起缩小——300 的 viewBox 里写 66px，容器一压就缩到十几像素，
手机上完全看不清。

- **百分比字号由 Python 按内径算好后内联**，CSS 里**不能**写 `font-size:46px`
  —— 同权重下 CSS 会盖掉内联样式，数字直接压在环上。
  内径 = `ring × 2(r − sw/2) / 300`（`r=118`、`sw=22`，即 `ring × 0.713`）。
  字符宽度按实测系数算（数字 0.575、点 0.30），不要用固定的 0.56。
- **字号下限必须跟着内径走**，不能写死 26px。
  环被挤到 96px 时内径只有 68px，26px 的「76.1%」宽 73px —— 数字压在环上。
  正确做法：内径装不下就先砍「口径」那行，再砍百分比字号。
- **环直径按宽度分，不按高度分**：`ring = min(168, max(88, min((w−16)×0.46, h−8)))`。
  环与侧栏是**并排**的，宽度上环占 46%、侧栏占 54%；
  高度上两者都能用满容器（侧栏用 `space-evenly` 均分）。
  之前按「高度减侧栏行数」倒推，侧栏 3 行要 186px，环被压到 96px —— 就是数字压圈的根因。
- **环内不放口径文字**。环心只放百分比这一个数。
  口径与侧栏信息重复，而且会被压到 15px（手机约 4pt，看不清）。
- 侧栏用 `.mn-ringside-fill{justify-content:space-evenly}` 跟着环高均匀分布，不挤在顶部
- 说明文字（caption）另起一整行，**不能塞在右列里**（会折成 3 行把列撑爆）
- 结构必须是「环 + 侧栏一行、说明另起一层」的两层，不能用 `flex-wrap`

### `grid` 指标网格

隔夜十项一览。2 列 × 5 行，`grid-auto-rows:1fr` 自动等高。每格 = 指标名 + 数值 + 涨跌 + 状态标签。

5 列时指标名会被截断（「美债」只显示一个字），保持 2 列。

**行高必须按 73px 预算**（`scrollHeight` 实测 72px = 40px 数值行 + 25px 名称行 + 18px padding，
再加 1px 边框）。`grid-auto-rows:1fr` 会把可用高度平均分给各行——
容器一旦比 `行数 × 73` 矮，格子就被压到内容高度以下，**数值行直接压在名称行上**。
这种叠字每一行文字自己都没超出父容器，「截断」检查抓不到，
只有 `audit_layout.cjs` 第 2.5 项（查 `.gc` 的 `scrollHeight`）才抓得住。

网格是宽表（`layout:"wide"`），需求里必须**加上方的文字块高度**，
漏掉就会把网格压扁。

### `photo` 配图

真实图片，base64 内联。`src` 可写相对 `data.json` 的路径或绝对路径。

### 视觉件通用规则

- **标题即结论**：`title` 写「离岸人民币破 6.68」，不写「美元兑人民币走势」
- 大数字必须带单位（`unit`），单位 26px 跟在小数字右侧基线上
- 视觉件下方的说明行（`.mn-cap`）是**浅色脚注**：`font-size:24px`、`color:#6B6558`
- **视觉件里不写来源、时点、口径**。`USDCNH 纽约尾盘`、`CME FedWatch · 10/20`、
  `纽约尾盘`、`截至 xx` 这类字样一律移到 footer —— 同一页里同一句话出现两次，
  读者只会觉得啰嗦。`build_cards.py` 预检会拦：
  `⚠️ 视觉件里写了来源「…」，来源统一放 footer`
- 保留在视觉件里的说明只允许是**读图口径**（`中轴为 0`、`两者几乎一样高 = 曲线更平`），
  且 **≤ 16 字**（超过就折行，把面板撑爆）
- **不许靠 `justify-content:center` 蒙混**：那会让内容堆在上半部分，下半张面板全空。
  这是本流水线最常见的版面事故。`audit_layout.cjs` 的第 2 项（留白）专查这个
- **左侧文字列（`.it-l`）用 `justify-content:flex-start`**，不要用 `center`：
  一条被拉高的 item 里文字垂到中间，看着像掉下去了

### 深红预算：一张卡最多 3 处

| 必留 | 可留 | 删掉 |
|---|---|---|
| banner 满宽（品牌识别） | 标题里的 `[[关键词]]` | 折线**面积填充** |
| 视觉件主色（线身/环） | 条形图主系列 | 第二个视觉件的重复着色 |
| | 结论条左边框 | 装饰性小色块 |

**语义标签不占深红预算**：2026-10-22 起四档标签改用四色墨（见第 5 节），已不含品牌红。
新加任何深红装饰前先数一遍：这一张已经有几处红？超过 3 处就换成 `#1F497D` 或灰。

## 6.5 要点层（`.it-pts`）

每条讯息的左侧文字列是三层结构：

```
窗口  汇率                                    ← 眉标行 = 语义标签 + 分类标题
离岸人民币破 6.68，四年最强                    ← 结论句（36px 粗，单行）
换汇成本正处在近几年最舒服的位置                ← 解释句（28px，单行，≤18 字）
· 四年区间 6.55–7.43，现在在下沿                ← 要点层（24px 灰，1–3 条）
· 10 万美元比 2025/04 高点少付 7.5 万
· 年内已升值 3.2%，2022/06 以来最快
```

**眉标行是两个东西拼起来的，不是两种标签**（2026-10-22 胡子哥纠正）：

- 左边「窗口」= **语义标签**（四档之一，彩色胶囊，见第 5 节）
- 右边「汇率」= **分类标题**（26px / 700 / `#2E2E2E`，纯文字、无底色）

分类标题属于**标题层级**，不进四档体系，也不需要配色。**别把它当成「没上色的标签」去凑色**。
唯一要守的分寸：它字号 26px 比标签 24px 大是刻意的层级差；哪天看着「分类标题压过彩色标签」，
优先把字重从 700 降到 500，不要动字号（动字号会改变 `.it-k` 行高，牵动整条竖向预算）。

**为什么要有这一层**：只有「结论句 + 解释句」时，左栏填充率只有 47–75%，
每条空着 78–166px。读者看到的是「就这一句话，没别的了」。

### 三层各司其职

| 层 | 写什么 | 不写什么 | 高度 |
|---|---|---|---|
| `title` 结论句 | 是什么 | 不写细节数据 | 47/行 |
| `desc` 解释句 | **一句钩子**，≤18 字 | 不重复 title，不堆数据 | 42/行 |
| `points[]` 要点 | 具体数据、对比、判断 | 不重复 title / desc | 35/条 + 23 头 |

**`desc` 必须压到单行**。实测 2 行就是 84px，是左栏最大的单项开销；
压到 1 行省下的 42px 正好够再放两条要点 —— **信息量不减反增**，
数据全部下沉到要点层。

### 样式

```css
.it-pts{flex:1 1 auto;min-height:0;display:flex;flex-direction:column;
  justify-content:space-evenly;gap:9px;margin-top:11px;padding-top:11px;
  border-top:1px solid #E9E2D4}
.pt-dot{flex:0 0 auto;width:7px;height:7px;margin-top:11px;background:#6B6558;
  border-radius:1px;transform:rotate(45deg)}   /* 菱形小方点 */
.pt-t{font-size:24px;line-height:1.45;color:#6B6558}
```

`flex:1 + space-evenly` 的作用：卡片被拉高时要点自动摊开，而不是底部留白。

### 要点条数按可用高度自动降档

`render_item()` 里按分到的高度算能放几条，**装不下就少渲染一条**：

```python
base = left_natural_h(item, w_left)     # 含全部要点的需求
while len(pts) > 1 and base > avail:
    base -= PTS_ROW + PTS_GAP
    pts = pts[:-1]
```

**绝不裁字** —— 裁字比少一条难看得多。预检会报
`⚠️ 要点渲染 2/3 条 —— 版面装不下，砍要点或砍别的内容`。

### 要点必须一行放得下

约 19 em 以内。写成完整句子会折行，既把空吃掉又撑破容器。
预检用 `est_lines()` 判断（不是数字数）——「道指 +1.02%，标普 +0.28%」有 18 个字符
但只占 11 个字宽，一行放得下，按字符数判断会误报。

## 7. 文字区与视觉件不许说同一个数字

01 号卡曾让折线画 7.4290 → 6.9757 → 6.6748，数字板再把同三个时点换算一遍，
解释句又说「比高点少付 7.5 万元」——读者读了三遍同一件事。

- **解释句可以复述视觉件**（解释句就是摘要），**但同一个数字出现两次就多余**
- 解释句写「所以呢」，不写「是什么」
- `audit_layout.cjs` 第 7 项检查两处：结论条 `.strip` 与条目 `.it-desc` 各自复述视觉件里的
  ≥3 位数字就报 `[W] 信息重复`（年份如 2025 属误报，已加白名单）

## 8. 页脚只放两件套

| 位置 | 内容 |
|---|---|
| 第一行左 | **本页**数据来源（逐卡 `sources` 覆盖全局）。「数据来源」四字是**灰色** `#6B6558` |
| 第二行 | 风险声明正文（**没有「风险声明」这四个字**） |
| 右 | 微信二维码 **140px**（**没有「扫码加我微信」文字**） |

**footer 不放**：期号 `No.001`、红色页码 `NN / 04`、段落名（段落名在正文页右下角角标）。
期号只留在 banner 右上角。

早期版本 footer 高 342px，还塞了「截止时间」和「全期来源」，手机上占掉近五分之一屏——已砍到约 177px。
**不要往回加内容**：footer 一膨胀，正文页能放条目的空间就被挤掉。

## 9. 整幅阅读（不假设任何二次裁切）

**每一张图都是一张独立可读的长图。** 图交付出去之后可能被放在任何位置、被任何客户端
以任何方式缩放，**版面不能依赖「用户点开就能看到全部」这个假设之外的东西**。

### 由此推出的三条硬规则

| 规则 | 说明 |
|---|---|
| **主标题是每张图的第一眼** | 它在正文页顶部，必须单行、字号 34–52px 自适应、颜色有对比。不能被当成「点开才看到的东西」 |
| **核心数字必须在视觉件里** | 不靠「反正缩略图会裁掉底部」来安排位置。视觉件和数字的排布按完整长图判断，不按任何假想的裁切窗口 |
| **banner 与 footer 都是内容** | banner 是品牌识别与期号，footer 是来源与风险提示——都是这张图的一部分，不是装饰或留白 |

### 曾经踩过的坑（已修正）

早期整套版面是按「朋友圈 4 张图显示为 2×2 正方形缩略图、每张只显示中心 1:1」校准的，
总高 1735 时可见区间只有正文页 y ∈ [209, 1289]，于是推出过两条错误结论：

1. 「主标题在缩略图里会被整条切掉」→ 于是把主标题当成可以牺牲的
2. 「核心数字必须落在 206–1286」→ 于是版面上留出大片「反正会被裁」的死区

**这个渠道假设已经不成立了。** 现在的做法是每张图按完整长图设计：
主标题在顶部、内容在中间、来源在底部，一眼扫下去顺序自然，不需要点开。

> 如果将来要发到某个会二次裁切的渠道，**不要改回旧逻辑**——
> 正确做法是另出一版适配那个渠道的图，而不是让主图迁就某一个渠道的裁切规则。
> 本 skill 出的图是「渠道无关」的。
